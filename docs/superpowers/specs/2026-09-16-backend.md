# Utility Expense backend design

## Requirements derived from the supplied Flutter project
Support owner, manager, and renter sessions; one active house per account; house-isolated users, rooms, meter readings, bills, dashboard, activities and tariff configuration. Add renters before assigning rooms. Owners assign managers; owners/managers manage renters and rooms. Renters only access their own records. Preserve frontend design and existing backend collection names.

## Chosen architecture
Use a modular NestJS 11 TypeScript application on Node 24, Firebase Authentication, Firebase Admin SDK, Firestore and private Firebase Storage. Preserve the supplied backend rather than rewrite it or migrate to SQL. Controllers validate requests; services enforce business rules; Store and Auth/Storage gateways isolate Firebase. Firebase client authentication handles signup/login/reset/refresh; backend verifies verified, non-disabled accounts and enforces membership from Firestore. Roles are never trusted from client input.

Alternatives considered: a full replacement risks existing data compatibility; SQL migration adds unnecessary migration and operations work. Incrementally hardening the existing modular backend is the smallest scalable option.

## Contracts and data integrity
Keep /v1 routes and existing houses/profiles schema. Add an explicit vacant-member workflow with transactional room assignment. Preserve integer Wh/paisa calculations, preview/publish, optimistic revisions, monthly uniqueness and idempotent retries. Transactions recheck access and read before writing. Use bounded cursor lists and indexed queries. Staff read household data; renters cannot access other residents' records. Add reports from persisted summaries rather than unbounded bill scans.

## Operations
Backend-owned environment configuration for the existing Firebase project. Never package service-account private keys. Separate health (process) and readiness (Firestore availability). Add bounded connectivity diagnostics without writing live data. Provide environment examples, production container, CI, Firestore indexes/rules, API contract, client mapping and setup/deployment instructions. Preserve supplied original files in inspection.

## Scope boundary
Deliver complete backend source, tests and documentation. The supplied Flutter uses synchronous local repositories and has no Firebase client configuration; it is not already network-connected. Do not pretend backend delivery switches Flutter to a remote data source. Document the exact asynchronous repository integration needed without changing its UI or shipping untested Flutter code. Account creation uses Firebase client SDK then verified-email membership assignment; invitation-based account provisioning is outside this smallest version.

## Verification
Run baseline tests, regression tests for each new workflow, typecheck, build, dependency audit and real Firestore emulator integration if tooling is available. Run only read-only live Firebase diagnostics with supplied credentials, keeping secrets out of logs and artifacts. Distinguish source/test readiness from live deployment, index provisioning and Flutter integration.
